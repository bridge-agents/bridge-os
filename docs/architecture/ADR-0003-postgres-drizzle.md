# ADR-0003: PostgreSQL as the only database; Drizzle ORM with SQL migrations

Status: accepted (2026-08-12); **amended by [ADR-0009](ADR-0009-embedded-database.md)**

> Amendment: "one PostgreSQL" still holds, but "a Postgres *server*" does not.
> ADR-0009 adds an embedded PGlite driver so desktop installs get the same
> Postgres dialect, schema and migrations with no service to run. Read the two
> together: everything below about Drizzle, jsonb manifests and SQL migrations
> is unchanged.

## Context
Bridge needs relational data (workspaces, agents, runs), document storage
(manifests), an append-only event log, and later vector search — while
staying `docker compose up`-simple for self-hosters.

## Decision
- **One PostgreSQL** (17) for everything: relational tables, `jsonb`
  manifests, events/audit log, and later `pgvector` for memory/knowledge.
  No second database until measurement demands it.
- **Drizzle ORM**: SQL-shaped, no codegen binary or query engine process,
  types inferred from the schema definition, first-class `jsonb`. Migrations
  are plain SQL generated by `drizzle-kit generate` and applied with
  `drizzle-kit migrate` — inspectable, reviewable, and runnable in CI and
  self-host installs.
- `postgres` (postgres.js) as the driver — small, fast, promise-native.
- Manifests are stored as `jsonb` (source of truth) with indexed relational
  columns (slug, status, spec_version) for querying. The DB never becomes a
  second schema authority: rows are parsed through `@bridge/spec` on read.

## Consequences
- Self-host stays one database container; desktop uses the embedded driver
  from ADR-0009 and no container at all. Cloud points the same code at
  managed Postgres.
- No Prisma engine downloads in Docker images; smaller, simpler builds.
- Multi-tenancy is enforced at the query layer (`workspace_id` everywhere)
  now; row-level security remains available in Postgres if Cloud needs it.
